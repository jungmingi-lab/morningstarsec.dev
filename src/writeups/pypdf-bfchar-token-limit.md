## 요약
**pypdf**의 **/ToUnicode** CMap 처리 코드에서 **bfchar** 항목의 개별 토큰 길이를 제한하지 않는 문제를 확인했습니다. 공격자가 조작한 PDF를 애플리케이션이 **extract_text()**로 처리하면, 압축된 작은 입력이 큰 문자열 디코딩과 임시 객체 할당으로 확장되어 메모리 사용량과 처리 시간이 증가할 수 있었습니다.

이 문제는 공개 GHSA로 등록되었고, pypdf **6.18.1**에서 수정되었습니다.

## 발견 과정
해당 문제의 발견 과정은 다음과 같습니다.

처음부터 임의의 PDF를 대상으로 무작정 테스트하기보다는, pypdf에 이미 적용된 **/ToUnicode** 대용량 처리 관련 보안 수정 사항을 검토하면서 분석을 시작했습니다.

기존 수정에서는 **bfrange** 항목에 대해 소스 코드 토큰과 대상 문자열의 길이를 제한하고 있었습니다. 이에 동일한 CMap 데이터를 처리하는 인접 함수인 **parse_bfchar()**에도 같은 제한이 적용되어 있는지 비교했습니다. 

코드 흐름을 따라가던 중 **parse_bfchar()**에서는 토큰 길이를 확인하지 않은 채 PDF가 제공한 값을 **unhexlify()**로 변환하고, 이후 문자 인코딩에 맞춰 디코딩한다는 점을 확인했습니다. 반면 형제 함수인 **parse_bfrange()**에는 동일한 디코딩 단계에 도달하기 전 길이 검사가 존재했습니다.

이 차이가 실제 보안 문제로 이어지는 지 확인하기 위해 공격용 페이로드가 아닌 경계값 기반의 최소 테스트 입력을 구성했습니다. 해당 입력을 공개 API인 **PdfReader~~~text()**로 처리한 결과, **strict=False**와 **Strict=True** 모두에서 큰 토큰이 제한 없이 디코딩되는 동작을 재현할 수 있었습니다.

또한 같은 조건에서 이미 길이 제한이 적용된 **bfrange** 경로와 비교했습니다. **bfrange**는 재한 초과 입력을 빠르게 거부했지만, **bfchar**는 입력을 계속 처리하면서 훨씬 큰 메모리 할당과 처리 시간을 발생시켰습니다.

이를 통해 문제의 원인이 단순한 비정상 PDF 허용이 아니라, 동일한 CMap 처리 계열 안에서 보안 제한이 한 파서에만 적용된 범위 불일치라는 점을 확인했습니다.

## 영향 범위
문제가 발생하는 공개 처리 경로는 다음과 같습니다.

```text
조작된 PDF
-> PdfReader
-> 페이지의 폰트 리소스 로딩
-> /ToUnicode CMap 파싱
-> bfchar 토큰 디코딩
-> extract_text()
```
페이지에 실제 텍스트가 많지 않더라도 페이지 리소스의 폰트를 읽는 과정에서 CMap이 처리될 수 있습니다. 따라서 PDF 업로드, 미리보기, 검색 색인, 문서 변환처럼 서버가 신뢰하지 않는 PDf에 자동으로 텍스트 추출을 수행하는 서비스가 주요 영향 대상입니다.

이 문제는 코드 실행이나 정보 노출 문제가 아니라, 파서가 입력 크기에 비례하지 않는 자원 사용을 하게 되는 가용성 문제입니다. 실제 영향은 프로세스의 메모리 제한, 동시 처리 수, 작업 큐 구성에 따라 달라질 수 있습니다.

## 기술적 원인
기존 CMap 파서에는 전체 매핑 항목 수를 제한하는 검사가 있었습니다.
