퍼징을 글로만 읽을 때는 “입력을 많이 넣어 본다” 정도로 이해했다. 직접 해보니 중요한 것은 무작위 입력의 양보다 **프로그램의 새로운 동작을 찾아 다음 입력에 반영하는 과정**이었다. 이번에는 작은 C 프로그램으로 AFL++를 실행하고, 저장된 크래시가 어떤 조건에서 발생했는지 확인했다.

## 퍼징과 퍼저

**퍼징(fuzzing)**은 프로그램에 다양한 입력을 반복해서 넣고 비정상 종료, 멈춤, 잘못된 동작 등을 찾아보는 테스트 방법이다. **퍼저(fuzzer)**는 입력을 만들고 실행 결과를 수집하며 다음 입력을 고르는 도구다.

입력을 만드는 방식에는 기존 샘플을 조금씩 바꾸는 **변이 기반**과 형식이나 문법에 맞춰 새 입력을 만드는 **생성 기반**이 있다. 또 실행 결과를 어떻게 활용하느냐에 따라, 코드의 어느 부분을 새로 지나갔는지 확인하는 **커버리지 기반 퍼징**과 그런 피드백 없이 입력을 시도하는 방식으로 나눠 볼 수 있다. 이 구분들은 서로 배타적이지 않다.

내가 이해한 커버리지 기반 퍼징의 흐름은 다음과 같다.

1. 처음 입력인 시드를 준비한다.
2. 퍼저가 입력을 변형해 프로그램을 실행한다.
3. 새로운 실행 경로를 만든 입력은 보관하고 다시 변형한다.
4. 충돌이나 시간 초과가 나면 해당 입력을 따로 저장한다.

## 받은 자료 세 가지는 무엇이 다른가

| 자료 | 정체와 특징 | 살펴볼 때의 관점 |
| --- | --- | --- |
| [AFL++](https://github.com/AFLplusplus/AFLplusplus) | 커버리지 피드백을 활용하는 퍼징 도구 모음. 소스 코드를 계측해 컴파일할 수 있고, QEMU·FRIDA 등을 통한 바이너리 대상 방식도 지원한다. | 시드, 커버리지, 크래시 파일이 실제로 어떻게 이어지는지 실습하기 좋다. |
| [Jackalope](https://github.com/googleprojectzero/Jackalope) | Google Project Zero의 커스터마이즈 가능한 커버리지 기반 퍼저. TinyInst를 이용해 소스가 없는 바이너리도 대상으로 삼을 수 있고, 입력 전달 방식과 변이기를 바꿀 수 있다. | 바이너리 대상 분석이나 대상 프로그램에 맞춘 구성 요소가 필요할 때의 선택지를 보여준다. |
| [google/fuzzing](https://github.com/google/fuzzing) | 퍼저 하나가 아니라 튜토리얼과 예제, 개념 문서의 모음이다. libFuzzer 튜토리얼과 좋은 퍼징 대상 작성법 등을 담고 있다. | 퍼저를 고르기 전에 퍼징 대상 함수를 어떻게 만들지 공부할 수 있다. |

따라서 셋을 동일한 퍼저로 놓고 속도를 비교하는 것은 맞지 않는다. 특히 AFL++도 바이너리 대상 모드가 있으므로, “AFL++는 소스 코드가 필요하고 Jackalope는 필요 없다”처럼 단정할 수 없다. 이번 실습은 세 자료 중 **AFL++만 직접 실행**했다.

## AFL++로 직접 실행해 보기

실습 대상은 표준 입력에서 최대 16바이트를 읽고, 앞 네 글자가 `FUZZ`이면 의도적으로 `abort()`를 호출하는 작은 프로그램이다.

```c
char data[16] = {0};
size_t n = fread(data, 1, sizeof(data), stdin);

if (n >= 4 && data[0] == 'F')
    if (data[1] == 'U')
        if (data[2] == 'Z')
            if (data[3] == 'Z')
                abort();
```

중첩된 조건은 한 글자씩 맞아 갈 때 다른 경로를 만든다. 단순한 코드지만, 퍼저가 새 경로를 발견해 입력을 발전시키는 모습을 보기에는 적당하다. `abort()`는 **실습을 위해 넣은 종료 조건**이며 실제 제품에서 발견한 취약점이 아니다.

Ubuntu WSL에서 `afl-clang-fast`로 계측해 컴파일하고, `A` 한 글자를 시드로 시작했다.

```bash
afl-clang-fast target.c -o target
printf 'A' > in/seed
AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1 AFL_SKIP_CPUFREQ=1 \
  afl-fuzz -i in -o out -- ./target
```

WSL의 `core_pattern` 검사 때문에 처음 실행이 중단돼, 이 **연습 환경에서만** `AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES=1`을 사용했다. 이 설정은 검사를 건너뛰므로 크래시 감지가 지연되거나 누락될 수 있다.

실행 결과, 약 **113초 동안 323,425회** 실행했고 코퍼스에 입력 5개가 남았으며 크래시 입력 1개가 저장됐다. 퍼저 화면의 `saved crashes: 1`은 저장된 입력의 수이지 서로 다른 취약점이 하나 확인됐다는 뜻은 아니다.

저장된 입력은 **45바이트**였고 `FUZZ`로 시작했다. `afl-tmin`으로 같은 크래시를 유지하며 불필요한 부분을 지우니 **4바이트 `FUZZ`**만 남았다. 이 입력을 다시 `./target`에 넣었을 때 `abort()`가 재현됐다.

```text
시드 "A" → AFL++의 입력 변형 → "FUZZ..." 크래시 저장
        → afl-tmin으로 최소화 → "FUZZ" → abort() 재현
```

여기서 코드를 읽는 일이 필요했다. 크래시 파일만 보면 어떤 입력이 프로그램을 종료시켰다는 사실만 알 수 있다. `fread`가 표준 입력을 읽고, 네 조건이 순서대로 검사되며, 마지막에 `abort()`가 호출된다는 것을 확인해야 **왜 종료됐는지** 설명할 수 있다.

## 실습에서 배운 점과 다음 단계

이번 실습으로 시드 준비, 계측, 커버리지 기반 입력 변형, 크래시 저장, 최소화, 재현까지 한 번 이어서 확인했다. 다만 대상이 작고 종료 조건을 미리 심어 둔 프로그램이므로, 이 결과로 실제 소프트웨어에서 취약점을 찾을 수 있다고 평가할 수는 없다. Jackalope와 libFuzzer도 아직 직접 실행하지 않았으므로 성능 차이는 결론 내리지 않았다.

다음에는 입력을 실제로 해석하는 작은 오픈소스 파서를 골라 **정상적인 시드와 퍼징 대상 함수를 직접 구성**해 보려 한다. 그때는 실행 횟수만 보지 않고, 어떤 코드가 실행됐는지와 저장된 오류가 재현되는지를 함께 확인하고 싶다. 이후 소스가 없는 바이너리를 대상으로 삼을 상황이 생기면 Jackalope의 TinyInst 방식도 실습해 볼 계획이다.
